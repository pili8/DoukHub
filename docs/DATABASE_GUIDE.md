# 数据库字段说明与同步流程

> 最后更新：2026-08-28，对应代码版本 v2.2.3

## 三张表概览

| 表名 | 用途 | 关联键 |
|------|------|--------|
| share_cache（分享表） | 导入的分享码和手动备注 | share_code（唯一）、sec_user_id |
| account_cache（账号表） | 从分享表同步过来的账号 + API 拉取的详情 | sec_user_id（唯一） |
| cookie_cache（Cookie表） | 采集/同步时用的 Cookie | Cookie |

## 四步同步流程

### 步骤1：导入分享表
- 作用：文本 → 分享表
- 依赖：无（不依赖 TTD 和 Cookie）

#### 支持的三种输入格式

**格式1：JSON**（每行一条，`|` 后的内容忽略）

示例：`{"地址":"https://v.douyin.com/xxx","等级":"个2，图3","用户":"昵称","粉丝":"1.2万","作品":"50"}`

**格式2：标签+等级@分享码**（@分隔，逗号多标签）

示例：`个2，图3@https://v.douyin.com/xxx` 或 `个2@abc123`

**格式3：空格分隔**（旧格式，兼容用）

示例：`https://v.douyin.com/xxx 3 个人 拍`

#### 能匹配的字段

| 目标字段 | 格式1(JSON) | 格式2(@) | 格式3(空格) | 匹配规则 |
|----------|-------------|----------|-------------|----------|
| share_code | "地址" 或 "Share" | @后面的部分 | 第一个词 | 必填，提取后标准化去URL前缀 |
| 等级 | "等级"里的数字 | 逗号分隔每段的末尾数字 | 第二个词(纯数字) | 取1-4，超范围截断 |
| 标签 | "等级"里数字前面的文字 | 逗号分隔每段的文字 | 第三个词起 | 多个合并去重 |
| 账号名称 | "用户" 或 "名称" | 不支持 | 不支持 | 仅JSON |
| 粉丝数 | "粉丝" 或 "粉丝数" | 不支持 | 不支持 | 仅JSON |
| 作品数 | "作品" 或 "作品数" | 不支持 | 不支持 | 仅JSON |

#### 无法匹配的字段

| 字段 | 当前行为 |
|------|----------|
| 备注 | 无法导入 |

#### 等级与标签的解析规则

等级字段如"个2，图3"会被逗号拆分成多段，每段末尾的数字是等级值（取最大），数字前面的文字是标签。
- "个2" → 标签"个"，等级2
- "图3" → 标签"图"，等级3
- 合并后：标签["个","图"]，等级取max(2,3)=3

#### share_code 标准化

导入时自动去掉 URL 前缀（`https://v.douyin.com/`、`https://www.iesdouyin.com/share/user/`），去掉参数和尾部斜杠。如果是完整用户主页链接且能直接提取 sec_user_id，则跳过步骤2。

#### 去重规则

- 同一批输入里出现同一 share_code：计为"重复"，仍合并等级和标签，但不重复新增。
- 数据库里已有同一 share_code：计为"更新"，等级取高的，标签合并，不创建新记录。
- 曾被软删除的 share_code：计为"恢复"，恢复原记录并写入本次信息。

#### 导入统计口径

"总输入"按粘贴文本的非空行数统计；"新增 / 更新 / 恢复"表示实际写入的行；"重复"表示同批输入中重复出现的分享码；"失败"表示写入异常；"跳过"表示格式识别失败或缺地址。失败和跳过都会把具体行与原因写入导入日志。页面上的写入数 = 新增 + 更新 + 恢复，不包含重复。

数据库首页的分享表 / 账号表 / Cookie 表数量只统计未软删除的有效记录。

### 步骤2：解析分享表
- 作用：分享码 → sec_user_id（调 TTD API 解析短链接）
- 执行条件：sec_user_id 为空 且 share_code 不为空
- 跳过条件：已有 sec_user_id
- 依赖：TTD 服务
- 写入字段：sec_user_id、解析状态=已就绪、解析状态=解析失败（失败时）
- `解析状态`只表示步骤2这个动作是否成功反馈过；导入完整主页链接并直接提取到 ID，也视为解析成功

### 步骤3：同步账号表
- 作用：分享表 → 账号表 + 调 TTD API 拉详情（昵称/粉丝/作品/签名/头像）
- 执行条件：有 sec_user_id。`解析状态`不参与本步骤筛选，也不影响能否进入账号表
- 跳过条件：账号表已有该 sec_user_id 且 获取状态=已获取（仅跳过API调用，仍合并等级标签）
- 依赖：TTD 服务 + Cookie。TTD/Cookie 只影响详情获取；任一不可用时仍会创建/恢复账号、合并等级标签，仅跳过详情
- 写入字段：账号名称、平台、链接、sec_user_id、等级、标签、粉丝数、作品数、签名、头像、获取状态=已获取、获取状态=获取失败（失败时）

### 步骤4：更新账号表
- 作用：对未获取信息的账号重新拉取详情（步骤3的自动重试通道）
- 执行条件：有 sec_user_id 且 获取状态 != 已获取
- 跳过条件：获取状态=已获取
- 依赖：TTD 服务 + Cookie
- 写入字段：账号名称、粉丝数、作品数、签名、头像、获取状态=已获取、获取状态=获取失败（失败时）。调用 TTD 时使用账号表"平台"字段
- 手动用法：在表浏览中把"获取状态"改为"待获取"，然后执行步骤4，即可重新拉取该账号
- 步骤4只更新账号表，不写分享表

### 边界规则

- 步骤3缺 TTD 或 Cookie 时，不失败整单，只跳过详情获取。
- 步骤4按账号表"平台"调用对应平台的详情接口。
- 导入完整主页链接时，先按 sec_user_id 查重，避免与同一账号的短分享码记录重复。

## 错误处理机制

- 分享表的"解析状态"：解析失败时标记，已就绪时自动恢复
- 账号表的"获取状态"：获取失败时标记，已获取时自动恢复
- 每次失败覆盖上一次的状态，只保留最新一次

## 重复数据处理

- 同一 sec_user_id 在分享表中重复时（步骤2解析后发现）：合并等级（取高）和标签，软删除重复记录
- 导入完整主页链接时：先按 sec_user_id 查重，命中已有短分享码记录则直接合并，不新建第二条
- 同一 sec_user_id 在账号表中已存在时（步骤3）：合并等级和标签，不重复创建账号
- 软删除的账号重新出现时（步骤3）：自动复活已删除的记录，而非新建

## 两表关联关系

分享表和账号表通过 sec_user_id 关联。系统在执行步骤3时，一次性把账号表全部加载到内存做字典查找（O(1)），判断某条分享记录是否已存在于账号表。不需要在分享表里额外加"已同步到账号表"字段。
