# 账号解析流程健壮性修复方案

> 对象：账号四大解析步骤中的**后三步** —— ②更新分享表（解析 sec_user_id）、③生成账号表、④刷新账号资料
> 方法：隔离数据目录 + 独立端口起测试实例，实测复现，非纸面推演
> 日期：2026-09-17

| # | 结论 | 性质 |
|---|---|---|
| 1 | **第二步与 Cookie 无关。** `/douyin/share` 是纯重定向解析接口，不接受 Cookie 参数。第二步失败不可能是 Cookie 问题 | 实测确认 |

### 2.3 真实库现状（2026-09-17 逐条复验后修正）

分享表 1048 条：已生成 983、已就绪 17、**解析失败 47**、待解析 1。

47 条的**真实构成**（初版只抽样看形态，"绝大多数是截断垃圾"这个结论是偏的，以逐条复验为准）：

| 类别 | 条数 | 说明 |
|---|---|---|
| 格式残缺 | 19 | 1~5 字符的截断垃圾（`If` / `3` / `U` / `xo`），永远不可能解析成功 |
| 跳平台首页 | 14 | 短码有效但账号已注销/删除，TTD 静默跳 `www.douyin.com` |
| **非主页链接** | **12** | **链接完全有效**，但指向**作品/直播**（`/video/`、`/note/`、webcast 回放），本来就提不出 sec_user_id |
| 其实能解析 | 2 | 复验后成功拿到 sec_user_id（历史故障误判） |

> **结论修正**：需要终态化的是 33 条 + 2 条恢复，**不是"全部 47 条"**。
> 那 12 条不是"链接坏了"，而是**导入了作品链接**，语义上不能叫"链接失效"。

### 2.4 TTD 对"失效链接"的真实返回（直接探测）

| 输入 | HTTP | 返回体 | 含义 |
|---|---|---|---|
| 有效短码 | 200 | `{"message":"请求链接成功！","url":"https://www.iesdouyin.com/share/user/MS4w..."}` | 正常 |
| 不存在短码 | 200 | `url = "https://www.douyin.com"` | **静默跳首页**，提不出 sec_user_id |
| 不存在短码 | 404 | `{"detail":"Not Found"}` | **代理误路由**导致路由未匹配 |
| 有效 sec_user_id | 200 | 完整账号资料 | 正常 |

**注意**：TTD **没有**业务错误码，失败一律表现为"200 但 url 不是用户页"或"404"。DoukHub 必须自己从响应里辨别类型。

## 三、根因分析

### 根因 1 —— 错误信息被吞成空字符串

`collector.resolve_short_url()` 把所有异常统一压成 `return ""`：

```python
try:
    resp = await self._client.post(endpoint, json=payload, timeout=30)
    resp.raise_for_status()          # ← 404 在这里抛异常
    data = resp.json()
    return data.get("url", "")       # ← 值为 None 时返回 None，不是 ""
except Exception as e:
    _logger.warning(...)
    return ""                        # ← 状态码 / 原因全部丢弃
```

调用方只能看到"空字符串"，于是统一写成：

```python
reason = "TTD 返回空(服务不可用或超时)"
```

**后果（用户可见）**：不管是"这条链接死了"还是"TTD 挂了"，日志都是同一句话。用户自然只能猜"是链接问题还是 Cookie 问题"——而这两个猜测都不对。

### 根因 2 —— 失效链接被计入"服务故障"计数器

```python
if not sec_user_id:
    consecutive_ttd_failures += 1                        # ← 死链被当成 TTD 故障
    if await _handle_ttd_failures(...): return
```

`_handle_ttd_failures` 对**每一次**失败都执行 `await asyncio.sleep(失败次数 × 5)`，第 5 次触发 60 秒冷却，最多 3 轮。

**原理问题**：失效链接是**数据层面的永久事实**，等待再久也不会恢复。退避机制只对"服务暂时不可用"才有意义。

**后果（用户可见）**：点一次"解析"按钮，界面像死了一样几分钟不动，进度条只走了一小截。

### 根因 3 —— 失败记录没有终态

```python
to_process = [c for c in collections
              if c.get("解析状态") in ("待解析", "解析失败") ...]
```

"解析失败"是个**循环状态**：失败 → 下轮再试 → 再失败。47 条死链意味着**每一轮都要重新交一遍过路费**。

**后果（用户可见）**：每次运行都慢，且永远慢，与新增数据量无关。

### 根因 4 —— TTD 日志中的代理劫持特征（防御性）

初版方案把 TTD 日志里的这几行当成了"代理劫持"证据：

```
"POST /douyin/share HTTP/1.1" 200 OK
"POST http%3A//127.0.0.1%3A5555/douyin/share HTTP/1.1" 404 Not Found
```

经复核，**这条根因不成立，整条撤销**：

| 检查项 | 实测结果 |
|---|---|
| WinHTTP 代理 | `直接访问(没有代理服务器)` |
| 系统代理开关（WinINET） | `ProxyEnable = 0` —— 虽然填着 `127.0.0.1:7890`，但**是关着的** |
| 代理环境变量 | `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 全为空 |
| 2975 端口 | 当前无任何进程监听 |

那几行 404 的**源端口与紧邻的正常请求完全相同**（同一 httpx 连接），说明是**我方调试脚本**直接打到 TTD 5555 留下的记录，不是 DoukHub 的正常调用路径。

至于早期观测到的 `HTTP_PROXY=127.0.0.1:2975`：那是**我方（AI 运行环境）**注入的代理，只存在于调试子进程里；DoukHub 由用户自行启动、继承系统环境，本身不含代理。

**结论：与项目无关，无需任何代码改动。**（§2.4 表中"不存在短码 → 404"一行同源于我方探测环境。）

### 根因 5 —— Cookie 轮换不感知失效（第三步 / 第四步）

```python
cookie = cookie_list[i % len(cookie_list)]   # 纯按序号轮换
```

Cookie 失效时 TTD 的真实行为（日志实录）：

```
响应数据不是有效的 JSON 数据，请尝试更换 Cookie
正在进行第 1 次重试
响应数据不是有效的 JSON 数据，请尝试更换 Cookie
正在进行第 2 次重试
… 重复 5 次 …
获取账号失败
```

**TTD 内部会重试 5 次**才认输 —— 单条记录就可能耗掉几十秒。而 DoukHub 拿到失败后直接把账号标成"获取失败"，**不会换用下一个 Cookie 重试**。

**后果（用户可见）**：一个 Cookie 过期，整批账号全部"获取失败"，且过程极慢。

## 四、修复方案

### P0-1 让解析结果带上"失败类型"

`collector.resolve_short_url()` 改为返回结构化结果，而不是裸字符串：

```python
@dataclass
class ResolveOutcome:
    url: str = ""
    kind: str = "ok"      # ok | bad_link | ttd_down | ttd_http | bad_json | proxy_suspect
    detail: str = ""
```

判定规则（依据 §2.4 实测）：

| 条件 | kind | 处置 |
|---|---|---|
| 200 且 url 含 `/user/` | `ok` | 正常写入 |
| 200 且 url 为空 / 指向抖音首页（无 `/user/`） | `bad_link` | **跳过，不退避** |
| HTTP 404 / 5xx | `ttd_http` | 退避 |
| ConnectError / ReadTimeout | `ttd_down` | 退避 |
| 非 JSON 响应体 | `bad_json` | 退避 |

### P0-2 只有"服务层失败"才退避

```python
outcome = await s.collector.resolve_short_url_ex(share, platform)

if outcome.kind == "bad_link":
    # 永久失效：标记终态，直接继续下一条
    failed += 1
    s.db.update_collection(rid, {"解析状态": "链接失效"})
    tm.add_log(task_id, f"跳过(链接失效) {share}", "warning")
    continue                      # ← 不调用 _handle_ttd_failures

consecutive_ttd_failures += 1      # ← 只有服务层失败才计数
```

**这一步是解决"卡死"的核心**：失效链接从"等 25 秒 + 60 秒冷却"变成"立即跳过"。

### P0-3 引入"链接失效"终态 + 一次性清理

1. `to_process` 只取 `待解析` + `解析失败`，**不再取 `链接失效`** —— 保证死链只被处理一次。
2. 前端状态徽章增加"链接失效"（建议用灰色或橙色，与"解析失败"的红区分开）。
3. **一次性数据清理**：把现有 47 条中长度 < 6 或含非法字符的直接置为"链接失效"，避免继续拖慢每一轮。

### P1-1 收紧退避与冷却（✅ 已落地）

| 参数 | 原值 | 现值 |
|---|---|---|
| 退避基数 `TTD_BACKOFF_BASE_SECONDS` | 5 → 5/10/15/20/25s | **2 → 2/4/6/8/10s** |
| 连败阈值 `MAX_CONSECUTIVE_TTD_FAILURES` | 5 | 5（不变，但**只统计服务层失败**） |
| 长冷却 `MAX_TTD_RETRY_ROUNDS` | 3 轮 | **2 轮** |
| 长冷却时长 | 固定 60s | **递增：`15 × 轮次` → 15s、30s** |
| TTD 真挂时最坏耗时 | 约 8 分钟 | **约 2 分钟** |

递增语义保留（原设计意图），只是把量级压下来；单条记录仍然只试 1 次，
"轮次"是整批重来，与单条重试次数无关。

### P1-2 Cookie 失效自动轮换（第三步 / 第四步）

把"按序号轮换"改为"失败即换 + 记忆失效 Cookie"：

```python
bad_cookies: set[str] = set()
for attempt in range(min(3, len(cookie_list))):
    cookie = next((c for c in cookie_list if c not in bad_cookies), "")
    if not cookie:
        break
    info = await collector.get_account_info(sec_user_id, platform, cookie)
    if info and info.get("nickname"):
        break                              # 成功
    if is_cookie_failure(info):            # data 为空 / message 含 "Cookie"
        bad_cookies.add(cookie)            # 拉黑并换下一个
        tm.add_log(task_id, f"Cookie 失效，切换下一个（已拉黑 {len(bad_cookies)} 个）", "warning")
        continue
    break                                  # 其他原因失败，不换 Cookie

if len(bad_cookies) == len(cookie_list):
    tm.add_log(task_id, "所有 Cookie 均已失效，请更新 Cookie 表", "error")
```

配套：给 `collector.get_account_info` 增加 `is_cookie_failure` 判定 —— TTD 对 Cookie 失效返回"200 但 `data` 为空 / `message` 提示更换 Cookie"，这是可识别的信号。

### P2-1 ~~禁用环境代理继承~~ 已撤销（见根因 4）

```python
self._client = httpx.AsyncClient(timeout=300, trust_env=False)
```

本机回环请求不应受系统代理影响。同时把预检的 `httpx.AsyncClient(timeout=3)` 一并处理。

### P2-2 补全平台分支

`resolve_short_url` 对非 douyin / tiktok 平台直接返回空串，导致小红书短链（`xhslink.com`）在第二步**必然失败**。建议补上 xhs 分支或明确标注为"暂不支持"并给终态，而不是混进"解析失败"里反复重试。

### ⚠️ 实测暴露的新隐患

1. **TTD 不提供任何可区分信号**：对"不存在短码 / 已注销 / 有效短码"返回体**一模一样**
   （`{"message":"请求链接成功！","url":...}`），唯一差别是 `url` 里有没有用户主页特征。
2. **同一短码会分钟级翻转**：`X5QFMPd7e0` 在 11:31 解析成功（已恢复「已就绪」），
   11:39–11:41 连试 4 次全部跳首页。→ **单次失败判死不绝对可靠**。
3. **应对措施**：判死前自动复认一次；日志附回退提示；表里支持把「链接失效」批量改回「待解析」。
   代价是真死链每条多花一次请求（一次性，判终态后不再产生）。

### 遗留

1. **12 条非主页链接**未处理：直接跑第二步会被判成「链接失效」（语义不准），建议单开一个终态取值。
2. **飞书侧存量「解析状态」字段仍只有 5 个选项**（`ensure_fields` 只建字段、不改选项），首次同步新值时是否报错待观察。
3. 正在运行的实例仍是旧代码，**需重启 DoukHub 生效**。
